# Whereto Admin

> Quick summary of the October 2026 security, payments, database and login changes: [what-changed.md](what-changed.md).

Private operational dashboard at `/admin`, backed by `/api/v1/admin`: Overview, Users, Trips, Subscriptions, Payments, Jobs, Integrations, Activity log and Sign-in & security. The English UI uses the existing Nunito, pastel palette, illustrated logo and train doodle.

## Administrator access

Administrator access is based on the persisted `user.role` value (`admin` or `client`) and is checked on the server for every protected endpoint. Client-submitted role fields are not accepted. The configured `ADMIN_OWNER_USER_ID` remains a server-only compatibility path for the existing owner account; every administrator, including that owner, still needs verified email, an active account and session-bound TOTP proof.

The verified account identified by `ADMIN_OWNER_USER_ID` alone can create unlimited trips and run unlimited menu imports without subscriptions or credits. The exception requires the account's persisted email verification to be true; other administrators and verified clients keep their normal quotas. Shared provider and storage limits remain in force.

There is no public administrator signup or email-based promotion.

### Staff roles

The owner (`ADMIN_OWNER_USER_ID`) manages staff from Users → Manage: **Make administrator** for a verified, active account, and **Remove admin access** to undo it. Removing access ends that person's admin session immediately. Both actions need a reason and are recorded in the activity log. Other administrators can help clients (credits, suspension, session revocation) but cannot change roles, act on another administrator, act on the owner, or grant credits to themselves. Nobody can suspend the owner from the dashboard. A new administrator still has to set up an authenticator before admin opens for them. The isolated test administrator is `admin@test.com`; it is never created automatically and its password is supplied through `TEST_ADMIN_PASSWORD` rather than stored in source or printed by the setup command.

Set `TEST_DATABASE_URL` to a dedicated disposable database or schema whose name includes `test`, set `NODE_ENV=test`, and provide a unique test password of at least 16 characters. Apply migrations to that test target only, then run:

```sh
export DATABASE_URL="$TEST_DATABASE_URL"
npm run db:migrate
npm run test-admin:seed
npm test
```

The test seed refuses non-test environments and unmarked database/schema names. It creates the administrator only when absent, stores a Better Auth password hash, and leaves any existing account untouched. If `admin@test.com` exists without the admin role, is unverified/inactive, or has no password credential, setup fails with a conflict instead of changing it. Never point these commands at production or a shared application database. The test account can authenticate with the configured secret; its first access to `/admin` requires authenticator enrollment and session verification, just like any other administrator.

To sign in, run the local app with `NODE_ENV=test` and `DATABASE_URL` pointed at the same isolated test target, then use `admin@test.com` and `TEST_ADMIN_PASSWORD` on `/login`. For example:

```sh
export DATABASE_URL="$TEST_DATABASE_URL"
export NODE_ENV=test
npm run dev
```

If you need to reset its password, use the normal password-reset flow while the app is still connected only to that test target and copy the reset link from the API terminal (or from the local mailbox when `LOCAL_MAILBOX=true`). Update `TEST_ADMIN_PASSWORD` to match; the seed intentionally never overwrites an existing password.

For an existing verified account:

```powershell
npm run admin:owner -- owner@example.com
```

Restart the API after changing its environment. In production, set the ID through the hosting environment rather than copying a local `.env`.

For a new **localhost-only** owner:

```powershell
npm run admin:owner -- owner@example.com --prepare-local
```

This creates an unverified account without a password, prints the verification/password-setup link in the terminal, and configures its ID. It does **not** verify the email, choose a password, enable TOTP or issue an admin session. The command refuses production or an external mail provider.

Open the printed link; it verifies the email and then opens password setup. (With `LOCAL_MAILBOX=true` the same messages also appear at `/login?setup=owner&email=owner%40example.com`.) Then sign in and visit `/admin` to enroll an authenticator and save backup codes. Expired messages can be regenerated by rerunning local preparation while the account is unverified, or through the normal password-reset flow afterward.

Better Auth handles TOTP enrollment and login challenges. Admin separately verifies a code on the server and records a proof bound to the exact session ID. Password and Google sessions both require this proof. Read access lasts at most 8 hours; changes require verification younger than 10 minutes. Five incorrect admin codes lock verification for 10 minutes in PostgreSQL, with an additional HTTP rate limit. Backup-code login alone does not grant admin access. Password resets and password changes revoke admin verification; resets also revoke every session. Signed-in sessions cannot call Better Auth's code check once an authenticator is active, so codes can only be tried where attempts are limited. Removing an administrator authenticator, retrieving its secret or regenerating backup codes requires recent admin verification.

Lost authenticator/recovery access requires an operator recovery procedure; there is no public MFA bypass or impersonation endpoint.

## Intervention rules

- Grants, consumption and revocation hold a common PostgreSQL advisory lock per account. Database CHECK constraints protect balances. Unique resource keys prevent charging one trip/menu twice. Request keys plus fingerprints make retries idempotent and reject altered duplicate requests.
- Trips use lifetime free entitlement, then subscription, then bonus credits. Menus use normal allowance before bonus credits. Grants never expire; only unused credits can be revoked. Archiving/deleting trips does not restore credits or the free entitlement.
- Suspension preserves records, revokes sessions, blocks login/API access, and blocks owned-trip access for collaborators/public links. Reactivation restores still-valid links, not old sessions. Stripe billing is unchanged.
- Retry accepts only failed jobs and rechecks owner access, service dependencies and allowance. Queued/processing/completed jobs cannot be manually relaunched. Atomic worker claims, unique menus and credit ledgers prevent duplicate results/charges. Queued rows are durable dispatch intents recovered by the worker.
- A processing job with a missing heartbeat stays processing. Age is a warning, never proof it is safe to duplicate work. Confirm actual process termination operationally before database recovery.
- Integration pause blocks new reservations and dependent job starts. Work paused before starting is redispatched after resume. In-flight calls can finish; subsequent requests recheck controls. Manual planning remains usable. Storage controls gate writes; existing documents remain readable. Already-issued Google browser keys cannot be revoked with a toggle: restrict those keys and hard quotas in Google Cloud.
- Stripe resync reads current Stripe state and applies a short database transaction. It never creates a payment or manual paid flag. Signed webhook failures retain only type, subscription reference, status and a safe error code. Failed initial synchronization can also be retried in Subscriptions. Refunds and financial changes remain in Stripe.

## Data and definitions

Admin queries use allowlisted projections. Trip JSON becomes counts/lock booleans inside PostgreSQL: no destination, title, budget, itinerary, notes, private URL or document content is returned. Job input/output and raw errors are excluded. Enrollment is a separate uncached flow and the only admin response with authenticator setup material.

Activity history combines administrator interventions with client account, trip, sharing and document changes. Business changes and their audit rows share a PostgreSQL transaction where the application controls both writes. Authentication history records successful sessions, failed email/password sign-ins, logout, password changes and observed expired-session cleanup. Failed attempts intentionally do not persist the submitted email; their `userId` is null because the audit hook does not receive a verified user identity for a failed sign-in.

Login metadata is bounded at write time; the dashboard shows a masked IP address and a shortened user-agent. Passwords, TOTP codes, session tokens, cookies, private trip contents, document names and share tokens are excluded from activity metadata. Activity/login results are paginated and filterable by user, action/event and date range, with UTC storage and local-time display.

Application routes expose no audit edit/delete operation. This is application-level append-only behavior, not protection against a database owner or a compromised DB credential. Use separate least-privilege runtime and migration roles, backups, and PostgreSQL/provider audit or infrastructure logs if changes made directly in the database must also be attributed.

| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Verified users       | All currently verified accounts.                                                                                                                                                                                                                                                 |
| Trips created        | Selected 7/30/90-day period, including archived trips.                                                                                                                                                                                                                           |
| Active subscriptions | Active/trialing Stripe status with a future paid-through date.                                                                                                                                                                                                                   |
| Estimated MRR        | Known EUR recurring amounts; annual divided by 12; before tax, fees and refunds. Unknown prices are counted and excluded. Actual cash/refunds remain separate in Stripe.                                                                                                         |
| Funnel               | Accounts whose signup was observed in the period, then observed milestones. First-action events are only tracked for observed account creations. Missing legacy events are never inferred. Email verification uses its actual callback, not unrelated profile updates.           |
| Trend                | Jobs created per UTC day and their current failure state. Empty data stays empty.                                                                                                                                                                                                |
| Worker               | 30-second heartbeat; missing after 90 seconds.                                                                                                                                                                                                                                   |
| Provider usage       | Application reservations, not supplier invoices. Geoapify reserved credits; Groq 6,000 reserved tokens per chunk; Google Places issued discovery sessions, not all SDK requests; email messages; monthly bytes written, not bucket size; Stripe outbound application operations. |

Lists paginate 20 rows, filters persist in URLs, and polling runs every 30 seconds only while visible. Alerts at 80%/100%, stale synchronization, missing heartbeat and failed jobs stay in the dashboard. Configuration alone never makes a service healthy: status stays unknown until an application operation is observed. No synthetic health requests incur provider costs.

## Deployment

New hard ceilings: `STRIPE_MONTHLY_OPERATIONS`, `EMAIL_MONTHLY_MESSAGES`, `STORAGE_MONTHLY_WRITE_BYTES`. Geoapify/Groq/Google reuse existing ceilings. Dashboard limits cannot exceed the server maximum (32-bit counter ceiling); zero blocks new reservations. No automatic upgrade exists.

Migration `202609080003_admin` adds Better Auth 2FA, session proofs, suspension, credits, admin audit, integration controls, job attempts, heartbeat, milestones and Stripe processing metadata. Migration `20261014000000_auth_activity` adds the default-client role, login events and general activity audit table without deleting existing data. Run migrations before starting updated API/worker processes, using the explicitly intended database.

`/admin` and `/two-factor` are noindex; the service worker does not cache these pages or admin API responses. Admin loads as its own route chunk. External providers require their accounts/keys for live acceptance. Local mail/storage are labeled. Configure commercial taxes/registrations before live checkout; this change enables neither Stripe Tax nor paid provider upgrades.

## Verification

Run `npm run typecheck`, `npm run build`, and `npm test` with `TEST_DATABASE_URL` configured. Vitest refuses to start without a test-marked database/schema and redirects Prisma to that target rather than `DATABASE_URL`.

`tests/admin.test.ts` uses disposable accounts, authenticated HTTP and real PostgreSQL: authorization on every section; persisted-role authorization; independent session proof including a separately signed session; owner-secret access protection; fresh verification; repeated/concurrent credits; DTO privacy; suspension/shared links; ceilings/pause/manual editing; active/completed retry rejection; normal/bonus menu priority; audit immutability; login-event visibility; persistent TOTP lockout and foreign-origin rejection. `tests/account-settings.test.ts` covers client role-tampering rejection and login/logout event persistence.

Menu/export tests race actual worker functions. Menus verify one bonus consumption for concurrent duplicate imports and cached reuse after exhaustion. Billing verifies signed/duplicate webhooks, cancellation, parallel resync and failed-event recovery without retaining raw errors.

Browser checks: owner login → authenticator enrollment → independent admin verification; Overview, Users, Integrations and Activity log; compensation review/confirmation and refreshed balances; Escape/focus restoration; 1440px desktop and 390px mobile without horizontal document overflow. Motion CSS is restricted to `prefers-reduced-motion: no-preference`; Radix controls supply keyboard interaction. Live provider results are not simulated.

For repeatable browser checks, `scripts/admin-browser-fixture.ts` starts a separate local API on 3002 with disposable accounts. Point a separate Vite instance on 5174 to `WHERETO_API_TARGET=http://127.0.0.1:3002`. Stop the processes, then run the fixture script with `clean`. Never run this helper in production.
